# Katchy Sales Analytics: Project Workplan

Nov 5, 2026 · @kathleen

## Project overview

This project replaces Katchy's manual sales tracking with a web application that stores sales information in a SQL database and answers real business questions through queries and charts. It is both a working tool for the business and a public data science portfolio piece.

## What is Katchy?

Katchy is my small art business. Items sold are sticker sheets, die cut stickers, art prints, t-shirts and pins. 

**Goals**

- Document how sales were tracked before and why that broke down
- Design a clean database for products, sales, channels and costs
- Answer 5–8 concrete business questions with SQL and Python
- Ship a web app with a usable dashboard, publicly demo-ed on perturbed data
- Share what the data revealed about the business

## Phase 1: Current sales tracking procedure

Describe exactly how sales are recorded today, step by step, so the problems in Phase 2 are easy to see.

- Where each sale is recorded
- What fields are captured per sale, and which are often missing
- How costs (printing, packaging, shipping, platform fees) are recorded, if at all
- How often records are updated and reconciled
- Include a screenshot or sample of the current records (anonymised)

## Phase 2: Problems and limitations

List each problem with a real example or a number. Specific pain points make the solutions convincing.

Likely candidates to check against your own experience:

1. **Data is scattered** across platforms, markets and notes, so there is no single view of sales.
2. **Inconsistent records**: product names, dates and prices are written differently each time.
3. **Costs are not linked to sales**, so profit per product is unknown.
4. **Manual work is slow and error-prone**, time-consuming.
5. **No insight**: hard to tell which designs or events perform best.
6. **No stock visibility**: reprints are decided by gut feel.

## Phase 3: Solutions mapped to problems

Each problem gets one specific fix in the new system.

| Problem | Solution |
| --- | --- |
| Data scattered | One SQL database; import scripts for platform exports and market sales |
| Inconsistent records | Fixed product IDs, dropdowns and validation in the entry form |
| Costs not linked | Cost tables joined to products and orders |
| Manual reconciliation | Automated imports and summary queries |
| No insight | Dashboard with charts answering the Phase 4 questions |
| No stock visibility | Inventory table with low-stock alerts |

## Phase 4: Business questions

Each question becomes one SQL query and one chart in the app, which keeps the scope focused.

1. Which products and designs make the most **profit**, not just revenue?
2. How do sales and profit compare across channels (online, markets, consignment)?
3. What is the true cost per order once printing, packaging, shipping and fees are included?
4. How do sales change over time, and what is the effect of events like 11.11 or market days?
5. Which products are bought together?
6. When should each product be reprinted, based on sales rate and stock?
7. Are price changes or bulk supplier orders improving margins?

## Phase 5: Data model and schema

Design the database before writing app code, and include an ER diagram in the write-up.

| Table | Key columns |
| --- | --- |
| products | product\_id, name, type (sticker sheet / print), size, design, price |
| product\_costs | product\_id, supplier\_id, unit\_cost, effective\_date |
| suppliers | supplier\_id, name (anonymised as Supplier A, B…), category |
| channels | channel\_id, name (Shopee, Etsy, market, consignment) |
| events | event\_id, name, date, channel\_id (11.11 sale, craft markets) |
| orders | order\_id, date, channel\_id, event\_id, shipping\_cost, fees |
| order\_items | order\_id, product\_id, quantity, unit\_price |
| inventory | product\_id, stock\_on\_hand, reorder\_level |

Splitting orders from order\_items lets one order hold several products, which answers question 5.

## Phase 6: Data privacy (real vs perturbed datasets)

The real database stays private on your machine; the public demo runs on a perturbed copy generated by a script.

- Scale all costs and quantities by one secret factor so ratios and trends are kept
- Add a few percent of random noise per row so exact figures can't be recovered
- Keep selling prices real, since they are public in your shop anyway
- Replace supplier names with Supplier A, B, C
- Never commit the scale factor, random seed or name mapping (use a `.env` file and `.gitignore`)
- Run the analysis on both versions and confirm the conclusions match
- State clearly in the public write-up that values are altered

## Phase 7: Building the web app in stages

Build a small working version first, then add features. Each stage ends with something that runs.

1. **Database**: create the schema in PostgreSQL, clean the historical data, load it in
2. **Queries**: write and test one SQL query per business question
3. **Visualisations**: build each chart in Python (Plotly) from the query results
4. **Minimum app**: Flask app with one dashboard page showing the core charts
5. **Data entry**: a form to add new sales and costs directly into the database
6. **UI/UX**: HTML and CSS styling, navigation, filters by date, channel and product
7. **Extras**: inventory alerts, CSV import for platform exports
8. **Deploy**: host the public demo with the perturbed data

## Phase 8: Results and reflection

Close with what the data taught you about the business, which turns the project from a coding exercise into data science.

- Key findings, one per business question
- Decisions you made or will make because of them (pricing, reprints, which markets to attend)
- How much time the new system saves compared with the old process
- Limitations of the data and what you would improve next

## Setup: PostgreSQL, Git and GitHub

Do this once before Phase 7. Commands are for a terminal (Terminal on Mac, Git Bash or PowerShell on Windows).

### 1. Tell Git who you are

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
```

Use the same email as your GitHub account so commits link to your profile.

### 2. Create the local project

```bash
mkdir katchy-sales-analytics
cd katchy-sales-analytics
git init
python -m venv venv
```

Activate the virtual environment with `source venv/bin/activate` (Mac) or `venv\Scripts\activate` (Windows), then:

```bash
pip install flask psycopg[binary] pandas plotly python-dotenv
pip freeze > requirements.txt
```

### 3. Create the local database

```bash
createdb -U postgres katchy
```

Then create a `.env` file in the project folder holding your private settings:

```
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/katchy
PERTURB_SCALE=0.83
PERTURB_SEED=12345
```

### 4. Protect private files with .gitignore

Create `.gitignore` before the first commit, so secrets and real data never enter Git history:

```
.env
venv/
__pycache__/
data/real/
*.sql.backup
```

Keep real data in `data/real/` (ignored) and the perturbed copy in `data/public/` (committed).

### 5. First commit

```bash
git status
git add .
git commit -m "Initial project setup"
```

Check `git status` before every commit. If `.env` or `data/real/` appears in the list, stop and fix `.gitignore`.

### 6. Create the GitHub repo and push

1. On GitHub, click **New repository**, name it `katchy-sales-analytics`.
2. Leave README, .gitignore and licence **unticked**, since you already have files locally.
3. Copy the repo URL and run:

```bash
git remote add origin https://github.com/YOUR_USERNAME/katchy-sales-analytics.git
git push -u origin main
```

GitHub no longer accepts your account password here. Sign in through the browser prompt, or use [GitHub CLI](https://cli.github.com) (`gh auth login`) or a personal access token.

### 7. Everyday Git workflow

Work on one feature per branch, then merge it into `main` through a pull request:

```bash
git checkout -b feature/database-schema
# ...write code...
git add .
git commit -m "Add products and orders tables"
git push -u origin feature/database-schema
```

On GitHub, open a pull request, review your own changes, and merge. Then update your local copy:

```bash
git checkout main
git pull
git branch -d feature/database-schema
```

**Habits to practise**

- Commit small, working changes often, with messages that say what changed ("Add profit-by-channel query", not "update")
- One branch per phase or feature, matching the Phase 7 stages
- Use `git log --oneline` to read your history and `git diff` to check changes before committing
- Use GitHub Issues as your to-do list and close them from commits ("Fixes #3")
- Tag milestones, e.g. `git tag v0.1-mvp` then `git push --tags`
